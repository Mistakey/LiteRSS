# LiteRSS 以 FreshRSS 条目 ID 为身份，本地只推送用户意图

> Source: literss-rb0 (D6, D7)；规划地图 mrrss-280

MrRSS 以 URL（外加 `unique_id`）为文章身份，FreshRSS 条目 ID 只是可空的附加列；本地库既是服务端镜像，又在推送阶段被当作权威，每次同步后把「本地与远端的差异」写回服务端；待推送变更是只追加的动作日志。三层叠加出同 URL 条目跟随、有界重试、队列快照时机等一串补偿守卫，还有一个根本缺陷：拉取已读集失败，或拉取与推送之间别处读了文章时，差异推送会把服务端的已读改回未读。LiteRSS 决定：文章主键是 FreshRSS 条目 ID；服务端所有的列（订阅、标签、`server_read` 镜像）只由拉取写入；用户操作只写意图表 `pending_read`（每条目一行，UPSERT 保留最新值，`seq` 单调递增）与 `pending_mark_all`；显示状态 = 有意图用意图，否则用镜像。本地永远不因「与远端不同」就改服务端，只推用户明确做过的操作。

## 被否决的方案

- **以 URL 为主键。** FreshRSS 按 GUID 建条目，重发的文章会有多个同 URL 条目、各带读状态，按 URL 查找取到哪一条是任意的。更糟的是 greader 的 `edit-tag` 把非纯数字的 `i` 解析成 0 却无条件回 `OK`，用 URL 推状态会静默失效。现在同 URL 的条目各自保留，只在展示层折叠，标已读时展开到组内全部 ID。
- **拉取后做差异推送。** 即旧模型。只要一次拉取失败或一个时间窗，就把别处的已读改回未读；而 LiteRSS 最明确的验收正是「从不把别处的已读改回未读」。
- **「此篇及以上 / 以下标为已读」换算成 `mark-all-as-read` 的 `ts` 区间。** `ts` 按条目 ID（抓取顺序）截断，列表却按 `(published_at DESC, item_id DESC)` 排序，「以上」在抓取顺序里不是连续区间，换算必然多标或漏标。改为前端把快照范围内的 ID 列表发给后端，后端只对显示为未读的条目写意图，推送器每请求约 250 个 `i` 逐条推送。`ts` 只用于源 / 分类 / 全部订阅的「全部标为已读」，取该范围最新条目的抓取时间。

## 后果

- 拉取无条件覆盖镜像、不看队列；意图与镜像不在同一张表，「拉取覆盖未推送改动」这类问题不再存在。推送成功后按 `seq` 比较再删意图，推送在途时写入的新意图不会被误删。
- `edit-tag` 永远回 `OK`，无法确认生效。身份恒为条目 ID 时这不构成风险；万一没改成，下一周期的未读集会纠正显示。
- 批量已读的撤销在后端按批次做：内存保存「这次由未读变为已读的条目 ID」约 60 秒，重启失效；撤销时写回未读意图，尚未推送的 `pending_mark_all` 直接删除。
- 服务端已归档、本地仍在的文章「标为未读」不会生效，下一周期又显示已读；不专门处理。
- 服务端星标原样保留，LiteRSS 不读也不写。
