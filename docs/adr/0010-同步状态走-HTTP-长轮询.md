# LiteRSS 同步状态走 HTTP 长轮询，前端不依赖 Wails 运行时

> Source: literss-rb0 (D14)；规划地图 mrrss-280

LiteRSS 的同步由后端调度：启动、定时、从睡眠恢复、窗口获得焦点、托盘「立即同步」都可能触发，前端必须知道任何来源触发的同步状态。旧版靠两套前端轮询（500 ms 与 5 s），其中状态轮询只在设置页开启 FreshRSS 时才启动，托盘触发的同步结束后界面不刷新。决定：`GET /api/sync/state?since=<rev>`。后端维护状态快照（运行中、新条目数、待推送数、上次成功时间、错误、`legacy_running`）和单调递增的 `rev`；`since` 小于当前 `rev` 时立即返回，否则挂起约 25 秒，期间状态一变就返回，超时返回原快照；前端循环请求，出错退避重连。每个响应都完整结束，Wails 窗口与浏览器取证通道走同一条代码路径，前端保持纯 `/api` 客户端。

## 被否决的方案

- **Wails 事件。** 前端要依赖 `@wailsio/runtime`；浏览器取证通道收不到 Wails 事件，只能另写一套降级订阅，agent 取证时测到的是降级那套，不是用户实际运行的路径，抵消了取证通道的意义。
- **SSE。** Wails v3 在 Windows 上的资源服务器响应写入器故意不实现 `http.Flusher`：`Write` 只进内存缓冲，请求结束时才一次性交给 WebView2（源码注释原话 "a streaming response cannot work on Windows today"）。流式响应在主平台上要等请求结束才到达页面。绕路让 WebView 页面直连回环监听器属于跨源请求，会被回环防护拒绝；放开它等于允许其他网页跨源访问。
- **前端定时轮询。** 延迟和请求频率只能二选一；旧版两套轮询并存又漏接线正是它的代价。长轮询空闲时每 25 秒一个请求，状态一变就返回，延迟与推送相同。

## 后果

- desktopapi 不得设置短于长轮询时长的 `WriteTimeout`，否则挂起的请求被截断。
- 等待必须同时监听请求 context 与服务关闭信号，`Shutdown` 时唤醒等待者；否则 `Shutdown` 要等活动连接结束，退出最多多等 25 秒。
- 资源服务器每个请求单独一个 goroutine，挂起的长轮询不阻塞其他请求。这依赖 Wails 实现细节，升级 Wails 时要复查（见 [ADR 0011](0011-桌面壳继续用-Wails-v3-钉版.md)）。
- 长轮询是同源 `fetch` GET，浏览器不带 `Origin`，不需要为它放宽回环防护。
