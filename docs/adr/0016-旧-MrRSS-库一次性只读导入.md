# 旧 MrRSS 库一次性只读导入

> Source: literss-rb0 (D12)；规划地图 mrrss-280

LiteRSS 换了数据模型：文章主键从本地自增 ID + URL 换成 FreshRSS 条目 ID，已读拆成服务端镜像列加本地意图表，数据目录也随改名变为新位置。用户的旧库（2026-09-27 实测）有 10938 篇文章且全部已读，另有 509 条真正的英文标题译文、3422 条「已判定为中文」的标记、70 篇手动生成的摘要、48 MB RSS 正文和三份加密凭据。决定新建数据库，首次启动时在旧固定路径（可用环境变量指定）查找旧库，按表结构识别，只读打开并 `VACUUM INTO` 快照后单向导入选定数据：有条目 ID 的文章（无 ID 的 17 篇丢弃）、RSS 正文、标题译文、摘要、未同步的已读意图、白名单内的设置与凭据；导入后在 `meta` 记 `legacy_import`，不再查找。旧目录与旧库从不修改，旧版就是回退路径。

## 被否决的方案

**原地迁移旧库。** 主键与几乎每张表都要换，原地改表会同时踩到两个老坑：SQLite `DROP COLUMN` 不回收空间且旧迁移每次启动都重跑；正文整行替换会抹掉新增列。改名后数据目录本来就变了，新文件是自然落点。

**只靠从 FreshRSS 重新拉取。** 标题译文、摘要是本地生成的，凭据只存在本地，这些拉不回来；「已判定为中文」的记录丢失后还会被重新请求百度，纯属浪费。导入这些数据的成本几乎为零。

## 后果

- 导入必须先于第一个同步周期；探测到旧版正在运行时推迟导入、不写 `legacy_import`，并提示用户退出旧版。
- 导入的旧文章多数早于 90 天保留期且已读，会在第一个同步周期末尾被清理；这是接受的结果，不是导入丢数据。
- 凭据按旧格式解密后用新方案重新加密，失败只丢该项并在导入报告里提示重填；星标意图、翻译缓存、订阅源（由首次同步重建）与上次同步时间不导入。
- 测试只用按旧建表语句合成的旧库，agent 不读用户真实库。
