# LiteRSS 本地库是 90 天内 reading-list 的完整副本，按抓取时间清理

> Source: literss-rb0 (D9)；规划地图 mrrss-280

LiteRSS 有「未读 / 全部」两个视图，「全部」要能回看已读文章，但本地库不能无限增长。决定：「全部」视图只读本地库，翻页时不向服务端拉取。同步周期除了补未读集的内容，还做一次高水位扫描——从最新往旧读 reading-list 的条目 ID，读到「本地最大条目 ID − 10 分钟」（兜住 FreshRSS 并发刷新时晚提交的小 ID）或「现在 − 90 天」为止——期间新到的条目不论已读与否都落库。每个周期末尾清理：抓取时间早于 90 天、显示为已读、没有待推送意图的文章，连带正文、全文、译文、摘要删除。抓取时间 = 条目 ID ÷ 10^6 秒：FreshRSS 的条目 ID 就是入库时刻的「秒 + 6 位微秒」，每篇都有、单调、不受源里坏日期影响。90 天写死，与 FreshRSS 默认归档期 `keep_period = P3M` 一致。

## 被否决的方案

- **只下载未读集。** 在别的设备上读掉、而 LiteRSS 那段时间没同步（桌面关机过夜正是这种情况）的文章，下次同步时已不在未读集里，本地永远不会有，「全部」视图就缺文章。
- **按 `read_at` 保留。** 旧库没有这一列；别处读的只能记成「LiteRSS 发现它已读的时间」；导入的上万篇只能取导入时间，要再等一个保留期才开始清理，且彼此没有差别。按 `published_at` 也不行：源里的坏日期会让文章一入库就被删或永不清理。
- **可配置保留期。** 长于服务端归档期的那段只在本地有，对它们「标为未读」不会生效；短于它就丢掉与网页端一致的回看。90 天约 6000–13000 篇、30–60 MB，不需要设置项，也不需要第二条体积上限。
- **「全部」视图按需向服务端拉。** 回看范围不比本地长（服务端同样约 3 个月归档）；服务端续页按条目 ID 排序，与列表的 `published_at` 排序混在一起，快照会跳动；拉下来的条目要挂译文终究得落库；离线时「全部」视图会断。要看更早的文章，去 FreshRSS 网页端。

## 后果

- 未读文章不管多旧都不删。但 FreshRSS 默认 `keep_unreads = false`，积压 3 个月以上或每源超过 200 篇的未读会被服务端删掉：它们从未读集消失、镜像记为已读、随后按抓取时间清理，未读数会突然下降，原因在服务端。
- 很早抓到、最近才读的文章，读完不久就可能被清理；按「当天或几天内读完」的动线很少见，接受。
- `published_at` 只用于显示与排序：缺失、为 0、解析失败或晚于抓取时间 1 天以上时用抓取时间，更早的原样保留。
- 从旧 MrRSS 导入的文章走同一条清理路径：第一个周期末尾，抓取时间早于 90 天的已读旧文章（含其摘要）被删除。
