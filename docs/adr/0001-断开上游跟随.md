# 断开对上游 WCY-dt/MrRSS 的跟随

> Source: mrrss-275349

本仓库是 `WCY-dt/MrRSS` 的 fork，目标是精简成自用版本：计划删掉约四成后端代码（ai、translation、media 缓存、freshrss、discovery、summary、statistics、rsshub 等功能域），并加入上游没有的按站点规则全文抓取。2026-08-26 决定不再对上游做整体合并——`upstream` remote 保留，但只在遇到具体 bug 时 cherry-pick 单个提交。理由是上游的功能增量对自用场景基本没有价值，而大规模删除会让每次 release 合并退化成删除/修改冲突的手工消解；上游近期约 5 周发 5 个 release（v1.3.24 → v1.3.28），这笔税会按 release 周期反复支付。

## 被否决的方案

**继续整体同步，把删减克制在上游极少改动的叶子模块。** 即只删 integrations 五件套、statistics、rsshub，核心 `feed` / `article` / `handlers/core` 一行不动。这样 114 项设置最多降到约 85 项，「精简成自用版」基本落空。取舍点很直接：保住合并可行性，就等于保住那些要删的功能。

**保留代码，只做 UI 折叠或高级模式隐藏。** 复杂度仍在，维护与阅读成本不降，只是看不见。

## 后果

- 依赖升级、Wails 版本跟进、安全补丁从此自担。这是本决定的主要代价，且随时间累积。
- feed 解析的边缘案例修复需要自己发现自己修，或主动去上游翻提交。
- 可逆，但不对称：`upstream` remote 保留，随时能挑单个提交；而分歧越久，恢复整体合并的代价越高。删减一旦落地，实际上就回不去了。
- 自研功能（如全文抓取 P0–P2）不必再考虑回馈上游或保持接口兼容。
- **看到 `upstream` remote 配置齐全却落后多个 release，不要当成失修去「修复」。那是本决定的预期状态。** 需要上游某个修复时，走 cherry-pick 单个提交，不要 `git merge upstream/<branch>`。
