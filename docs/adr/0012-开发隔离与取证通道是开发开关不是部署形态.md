# LiteRSS 的开发实例隔离与浏览器取证通道是开发开关，不是部署形态

> Source: literss-rb0 (D5)；规划地图 mrrss-280

旧版在 agent 会话里启动开发构建时，停在 `Starting Wails v3...` 就退出，曾被记为「agent 环境起不来桌面应用」。实测原因是单实例锁：开发构建与安装版共用同一个 UniqueID，Wails v3 在 Windows 上抢不到命名互斥量，就通知已有实例（把用户窗口唤到前台）后 `os.Exit`；用户没开应用时，开发构建则直接打开用户的真实数据库并截断其日志。换掉 UniqueID 并隔离数据后，agent 会话能正常创建窗口、回环 API 返回 200，用户实例 PID 不变、真实 `%APPDATA%` 无新目录。决定：开发构建整体换一套身份——独立 UniqueID、portable 数据目录、独立 WebView2 用户数据目录、1235 回环端口，只连假 FreshRSS；已安装版本的 UniqueID 在 agent 会话里一律不得用于启动。浏览器取证通道：开发开关打开时由 desktopapi 回环监听器同时挂前端静态文件，入口统一写 `http://127.0.0.1:<端口>/`。回环防护改为：`Origin` 为空，或严格等于监听器自身的源才放行；拒绝 `Sec-Fetch-Site` 为 `same-site` 与 `cross-site`；保留回环 Host 检查；不认 `localhost` 别名。

## 与 ADR 0005 的边界

[ADR 0005](0005-只做桌面应用删除-server-与-docker-部署.md) 否决的是 headless 应用作为另一种运行形态（NAS / docker、`//go:build server`、两套路由配置）。取证通道是同一个桌面二进制、同一个 `main.go`、同一套路由；默认关闭，安装版不开启；只监听回环；没有无窗口运行模式，也不对外提供服务，因此不与 0005 冲突。有人想把它扩成可部署的 headless 服务时，适用的是 0005，不是本 ADR。

## 被否决的方案

- **Wails `-tags server` 作取证通道。** 实测能跑，但它没有任何 Origin 防护：带 `Origin: https://evil.example` 与 `cross-site` 的 POST `/api/settings` 返回 200；监听地址由环境变量决定，设成 `0.0.0.0` 就把无防护的 API 暴露到局域网。它还是另一种构建（无单实例、窗口、托盘，运行时走 WebSocket），多一个监听器，而且正是 0005 删掉的构建形态。
- **把回环防护放宽到 `same-site`。** 同一主机其他回环端口上的任何页面（例如另一个开发服务器）都是 same-site，放宽等于允许它们改设置、标已读。严格同源已经够用：旧规则「带 `Origin` 即拒」之所以连 CSS/JS 都拦成 403，是因为 Chrome 对同源 POST 与带 `crossorigin` 的同源资源 GET 也发送 `Origin`，改成与自身源严格相等即可放行。
- **只换数据目录、不换 UniqueID。** 单实例锁仍被用户实例持有，开发构建照样启动即退出。四样隔离缺一不可：不设 `WebviewUserDataPath` 时 WebView2 数据落到真实 `%APPDATA%\<exe 名>`；端口冲突时 desktopapi 只记日志继续运行，取证请求会打到用户实例的 API。

## 后果

- 需要热更新时，Vite 代理只把 `Origin: http://127.0.0.1:5173` 改写为目标监听器的源，其他 `Origin` 原样转发（仍被拒绝），不整体去掉 `Origin`；取证默认用「构建后由开发实例托管」。
- 取证通道只替代 agent 对界面与 API 的自动验证；原生窗口观感、托盘等仍需人工在真实桌面验收。
