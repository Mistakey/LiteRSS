# 已读文章保留与「全部」视图数据来源（mrrss-280.13）

> Epic mrrss-280「重做并精简 MrRSS」的规划节点产物。只给结论，不含目标代码。
> 输入：同步模型（`sync-model.md`，mrrss-280.2）、旧库迁移（`data-migration.md`，mrrss-280.10）、
> 功能与设置清单的用户裁决（mrrss-280.4，U7 保留「未读 / 全部」切换）。
> FreshRSS 行为以 `FreshRSS/FreshRSS` edge 分支源码为一手来源：`p/api/greader.php`、`app/Models/EntryDAO.php`、
> `app/Models/Entry.php`、`config-user.default.php`、`lib/lib_rss.php`（2026-09-27 读取）。没有读取用户的真实数据库，
> 涉及真实库的数字都引自 `data-migration.md`。

## 结论

1. **「全部」视图只读本地库，不在翻页时向 FreshRSS 按需拉已读条目。** 本地库改为「保留期内 reading-list 的完整副本」：
   同步周期除了补未读集的内容，还补**保留期内所有新到条目**的内容，不管它们在服务端是否已读。
   这修改了 `sync-model.md`「拉取与分页」第 4 步的「已读条目不下载」。
2. **保留期按条目的抓取时间计算，不按已读时间。** 抓取时间直接由 FreshRSS 条目 ID 得出（ID 就是入库时刻的微秒时间戳），
   每一篇文章都有，包括旧库导入的文章。因此不需要 `read_at` 列，`data-migration.md` 里「导入时 `read_at` 取导入时间」
   这条规则作废。
3. **保留期的数值由用户决定**（见 Q1）。推荐 90 天，与 FreshRSS 默认的归档期 `P3M` 一致。保留期写死，不做设置项。
4. **已取消订阅的源，其文章在下一次成功同步时从本地删除**（见 Q2），译文和摘要一起删除。
5. **`published_at` 只用于显示和排序，不参与清理。** 缺失、解析失败或晚于抓取时间一天以上时，用抓取时间代替。

## 为什么不按需拉取

「进入『全部』视图或翻到本地末尾时，用 `stream/contents?it=read&c=...` 向服务端取已读条目」技术上可行，但不推荐：

- **回看范围并不比本地更长。** 服务端默认 3 个月归档，而且按 `lastSeen` 清理；本地保留期可以等于或长于它。按需拉取只能在
  「服务端还在、本地已删」这段区间有用，而这段区间可以通过把本地保留期设成不短于服务端来消除。
- **与列表模型冲突。** `sync-model.md` 的列表是「进入视图时取有序 ID 快照，排序键 `(published_at DESC, item_id DESC)`」。
  服务端续页按条目 ID（抓取顺序）排，两种顺序混在一个列表里，要么顺序跳动，要么快照在翻页时变化，mrrss-zot 和 pitfall 15
  解决的问题会以另一种形式回来。
- **拉下来的条目终究要落库。** D1 要求列表显示中文译文，译文存在本地表里，以条目 ID 为键。远端条目不落库就没处放译文，
  落库则等于本地保留，只是换了一个更难预测的时机。
- **离线和慢网络下「全部」视图会断。** 本地读取没有这个问题。

真要回看保留期以前的文章，去 FreshRSS 网页端（与清单草案 U7 的说法一致）。

## 本地库补全：保留期内的新条目全部落库

只拉未读集有一个缺口：用户在别的设备（手机、FreshRSS 网页）上读掉的文章，如果 MrRSS 在那段时间没有同步过，
它们在下次同步时已经不在未读集里，本地永远不会有，「全部」视图里就缺了这些文章。桌面应用关机过夜、第二天早上开机，
正是这种情况。

补法（在 `sync-model.md` 的同步周期第 3、4 步之间加一步）：

1. 本地记一个**高水位** `max_item_id`：本地已有的最大条目 ID（含导入的）。
2. 取 `stream/items/ids?s=user/-/state/com.google/reading-list&r=d&n=<足够大>`，从最新往旧读，读到
   `id <= 高水位 − 重叠量` 或者 `id` 对应的抓取时间早于「现在 − 保留期」就停。重叠量取 10 分钟对应的 ID 差
   （`10 × 60 × 10^6`），用来兜住 FreshRSS 并发刷新时晚提交、ID 却较小的条目。
3. 这些 ID 里本地没有的，和未读集缺失的 ID 合在一起，按 `sync-model.md` 第 4 步的方式用 `stream/items/contents` 分批补内容。
4. 已读状态照常由未读集决定：不在未读集里的记 `server_read = 1`。

成本与「新到条目数」成正比，和只补未读集时相同量级（用户在 MrRSS 里读完的条目，本来就是作为未读补过内容的）。
首次同步（新装、或旧库导入后）也受保留期约束：不会把服务端的全部历史拉下来。

## 清理规则

在每个同步周期末尾执行，也就是 `sync-model.md` 第 5 步：

- **删除条件**：抓取时间（条目 ID ÷ 10^6，单位秒）早于「现在 − 保留期」，**并且**显示状态为已读（镜像 `server_read = 1`，
  且 `pending_state` 里没有这篇的 `read` 意图）。
- **不删**：未读的文章（不管多旧）、有待推送意图的文章。C2 删除收藏后不再有星标保护；有 AI 摘要的文章也不特殊保护，规则只有一条。
- **连带删除**：正文、全文缓存、译文、摘要，以条目 ID 为键的本地表一起删（外键 `ON DELETE CASCADE` 或同一事务）。
  删完做一次 `incremental_vacuum`（沿用现有做法）。
- **导入的文章走同一条路径**（`data-migration.md` 已定）：导入器不截断，第一次同步周期末尾的清理会删掉抓取时间早于保留期的已读旧文章。
  17 篇没有条目 ID 的文章本来就不导入，所以每篇导入的文章都有抓取时间。
- **不设单独的体积上限。** 清单把 `max_cache_size_mb` 改为「固定上限，自动清理」，时间窗口就是这个固定上限；
  按 Q1 各选项的体积估算都在几十到几百 MB，不需要第二条规则。
- **列表快照里的文章被清理掉**：只可能发生在快照最底部（最旧的那几篇），前端按 ID 取卡片时拿不到就跳过，不报错。
- **服务端已归档、本地还在的文章**：本地仍显示为已读。此时对它「标为未读」，edit-tag 服务端会回 `OK` 但没有效果，
  下一周期未读集里没有它，显示又回到已读。保留期不长于服务端归档期时基本碰不到，不专门处理。
- **服务端清掉的未读文章**：它会从未读集消失，镜像记为已读，随后按抓取时间清理。这与 FreshRSS 网页端看到的一致。

## 计时基准：为什么用抓取时间

| 候选 | 问题 |
| --- | --- |
| 已读时间 `read_at` | 旧库没有；在别的设备上读的只能记成「MrRSS 发现它已读的时间」，不准；导入时只能取导入时间，于是 1 万篇历史要再等一个保留期才开始清理，而且它们的保留期彼此没有差别。还要多维护一列 |
| 发布时间 `published_at` | 源里的坏日期会让文章一入库就被清掉（`2001-01-01`）或永不清理（未来日期）；旧库存的是 Go `time.Time` 的字符串，要解析 |
| **抓取时间（条目 ID）** | 每篇都有、单调、不受源影响，与 FreshRSS 自己的归档口径（`lastSeen`，通常等于或晚于抓取时间）接近。代价是：一篇很早抓到、最近才读的文章，读完不久就可能被清掉。按用户的动线（未读当天或几天内读完），这种文章很少 |

## `published_at` 的处理

- 同步来的条目取 API 的 `published`（Unix 秒）。旧库导入的按 Go `time.Time` 的字符串格式解析（`data-migration.md` 已写明格式）。
- 缺失、为 0、解析失败，或者晚于抓取时间 1 天以上：改用抓取时间。
- 早于抓取时间很多的（例如 `2001-01-01`）**原样保留**：它只影响排序（沉到列表底部），不影响清理，因为清理按抓取时间；
  也可能是源里真实的旧文章（新订阅时回填）。不为猜测坏日期另设规则。

## 已取消订阅的源

- FreshRSS 删除订阅时，服务端会删掉该源的条目，网页端也看不到了。
- 推荐：同步周期第 2 步（`subscription/list`）**成功**后，本地删除所有 `stream_id` 不在返回列表里的文章，连带正文、译文、摘要，
  以及这些条目的 `pending_state`（服务端已无此条目，推送无意义）。
- 防误删：只有 `subscription/list` 返回 2xx 且解析成功时才执行；返回的订阅数为 0 而本地原有订阅时跳过这一步并记日志，
  避免服务端异常时清空本地库。
- 旧库导入的文章同样适用：第一次同步后，指向已不存在的 stream ID 的文章会被删掉。
- 不推荐「保留到保留期、显示为未知订阅」：侧栏按订阅分组（U8），这类文章在侧栏里没有位置，只会出现在「全部订阅」里，
  用户也没法对它们做任何有意义的操作。

## 给用户的选择

### Q1 · 「全部」视图能回看多久以前的文章

「全部」视图只显示本地保存的文章。已读文章在**抓取后**超过这个期限就会从本地删除（未读的不删）。
估算依据：真实库 2026-09 前 26 天入库 3658 篇、2026-08 入库 2133 篇（按发布时间），即每天约 70–140 篇；
每篇正文平均约 4.8 KB。选定后写死，不做设置项。旧库导入的 10938 篇里，抓取时间早于期限的会在第一次同步后删掉（包括其中的 AI 摘要）。

- **A · 30 天** — 约 2000–4000 篇、10–20 MB。导入的历史大部分会被删掉，只剩最近一个月。
- **B · 90 天** — 约 6000–13000 篇、30–60 MB。与 FreshRSS 默认归档期（3 个月）一致，本地能看到的和网页端基本相同；导入的历史保留最近 3 个月。
- **C · 1 年** — 约 2.5–5 万篇、125–250 MB。超过服务端默认归档期的那部分只在本地有，对它们「标为未读」不会生效。
- **D · 不自动删** — 数据库每年增长约 0.1–0.25 GB，没有上限；问题同 C。

➡️ **推荐 B**：回看的实际用途是找回误标已读和「前几天那篇」，3 个月足够，而且与服务端口径一致，不会出现本地有、服务端没有的状态。

---

### Q2 · 取消订阅的源，本地文章怎么处理

在 FreshRSS 里取消订阅后，服务端会删掉该源的全部文章。

- **A · 下次同步时删掉** — 与 FreshRSS 网页端一致；侧栏里没有这个源，文章也一起消失。已生成的摘要随之删除。
- **B · 保留到保留期结束** — 在「全部订阅」里还能看到，但源名显示为「未知订阅」，侧栏里找不到它。

➡️ **推荐 A**：取消订阅就是不想再看；B 的文章在按订阅分组的侧栏里无处安放。

## 新发现（未入图）

1. **FreshRSS 续页在边界条目状态变化时会漏一条。** `c` 是包含上界，服务端无条件丢掉结果的第一条（`greader.php` 约 713–728、
   812–827 行）。如果作为续页边界的那篇条目在两页请求之间不再满足过滤条件（例如取未读集时它在别的设备上被读掉了，
   或者被服务端归档删掉），下一页的第一条就是一篇没发过的条目，却被丢掉了。对 `sync-model.md` 的未读集扫描来说，
   这意味着一篇未读会被误记为 `server_read = 1`，直到下个周期才纠正（如果它仍然未读）。修法：取 ID 集时把 `n` 设得足够大
   （服务端不设上限，ID 每条约 20 字节，5 万条约 1 MB），让一次请求取完，不依赖续页；只有超过这个量时才续页，并接受这个边角情况。
   这是对 `sync-model.md`「拉取与分页」第 3 步「用 `c` 续页」的修正。
2. **服务端默认会清掉未读文章。** `keep_unreads = false` 是 FreshRSS 的默认值：3 个月以上、或每源超过 200 篇的未读也会被删。
   对新模型没有破坏（未读集里没有就当已读），但用户如果积压未读，会看到未读数突然下降，原因在服务端。用户实例的归档设置没有核实。
